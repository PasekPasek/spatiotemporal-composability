A walkthrough of arXiv:2608.25512 (Shi, Zhang and Cui, 2026)

Spatiotemporal composability

You disable a plugin in your editor and it asks you to restart. The code is gone, but nobody knows what that plugin changed. This page shows a runtime that does know.

The idea fits in two rules. Every change a component makes returns its own undo, and the runtime keeps those undos on a stack. Every component declares what it needs, and the runtime starts or stops it as those needs appear and disappear. With both, you can add, replace and remove parts of a running program, and nothing leaks.

Five live sandboxes follow. Each one isolates one mechanism. The last one runs them all on an agent harness that redeploys its own tools while it serves requests.

01

The problem

Plugin code changes things and forgets how to change them back.

Here is an ordinary plugin. It makes three changes to the program around it:

export function apply(bus: Bus, services: Registry) {
  bus.on('message', onMessage)
  const timer = setInterval(poll, 1000)
  services.db = new Database()
}

To remove it cleanly, someone must write a dispose() that undoes all three. In practice nobody keeps it in step. You get a leaked listener, a timer that never stops and a dead entry in the registry. A restart is the only safe cleanup.

The paper splits the problem along two axes:

  • Time. Removing a component must undo everything it did. The mechanism is revertible effects: each change carries its own inverse, and the runtime holds on to it. Section 02.
  • Space. A component declares what it needs from its environment. The mechanism is reactive coeffects: the runtime watches those needs and starts or stops the component as they change. Section 03.

An effect is what a component does to its environment. A coeffect is what it needs from it. Both go through one shared object, the context. The paper calls this discipline the context paradigm.

Going deeper: the context paradigm

A coeffect is the dual of an effect — the dual notion, familiar from static analysis, lifted here into a runtime mechanism.

The paper's own move is to unify the two axes rather than bolt them together: the effect context and the coeffect context collapse into a single context type, and every effect and every coeffect is mediated through it. That mediation is what induces the observational equivalence up to which two components' effects interleave without disturbing one another.

02

Every change returns its undo

The context keeps its state and, next to it, a stack of inverses.

Two operations do all the work. track(f, g) applies the change f and pushes its inverse g onto the stack. recover pops the inverses and runs them, newest first. Order matters: you undo the last change first, like any stack.

      Apply a few changes, then undo them one at a time.

      In Cordis, the TypeScript reference implementation, a component writes the change and its inverse in one place. The context APIs already know their own inverses:

      export function apply(ctx: Context) {
  // an explicit effect: the change and its inverse together
  ctx.effect(() => {
    const timer = setInterval(poll, 1000)
    return () => clearInterval(timer)
  })

  // context APIs are tracked already: the runtime derives the inverse
  ctx.on('message', onMessage)
  ctx.set('db', new Database())
}

      The whole mechanism, in one class

      Without the ergonomics, the mechanism is a stack of functions. set, on and use never touch the stack themselves. All three call effect:

      type Dispose = () => void
interface Component { apply(ctx: Ctx): void }

class Ctx {
  private phi: Dispose[] = []                      // φ: the undo stack
  private sigma = new Map<string, unknown>()        // Σ: the services provided
  private watchers = new Map<string, Set<Dispose>>()
  constructor(private bus: EventTarget) {}

  /** track(f, g): run the change, keep the inverse, hand it back */
  effect(f: () => Dispose): Dispose {
    const g = f()
    let armed = true                                // an inverse runs at most once
    const dispose: Dispose = () => { if (armed) { armed = false; g() } }
    this.phi.push(dispose)
    return dispose
  }

  /** providing a service is itself a revertible effect */
  set(key: string, value: unknown): Dispose {
    return this.effect(() => {
      const had = this.sigma.has(key), prev = this.sigma.get(key)
      this.sigma.set(key, value)
      this.notify(key)
      return () => {
        had ? this.sigma.set(key, prev) : this.sigma.delete(key)
        this.notify(key)
      }
    })
  }

  /** a tracked context API: the caller never writes this inverse */
  on(event: string, fn: () => void): Dispose {
    return this.effect(() => {
      this.bus.addEventListener(event, fn)
      return () => this.bus.removeEventListener(event, fn)
    })
  }

  /** starting a component is not a new mechanism: it is one more effect */
  use(component: Component): Dispose {
    return this.effect(() => {
      const child = new Ctx(this.bus)
      component.apply(child)
      return () => child.recover()             // the child's whole stack, as one inverse
    })
  }

  /** recover: run the inverses, newest first */
  recover(): void { while (this.phi.length) this.phi.pop()!() }

  /** the dependency side, in outline only: section 03 covers it */
  private notify(key: string): void {
    this.watchers.get(key)?.forEach(fn => fn())
  }
}

      Three details matter:

      • Each method returns its inverse. You can withdraw one effect and leave the rest alone.
      • An inverse runs at most once. Cordis calls this the armed flag. A second run would meet a state that the effect never produced.
      • A component is an effect that owns a context. use gives each component its own child context and stack. The inverse of use drains that whole stack. This is how you remove one component without touching the others.
      Going deeper: why the paper does not stop here

      An ordinary context Γ is lifted to a revertible one, ∂Γ = Γ × (Γ → Γ): the current state γ together with φ, the composition of the inverses of every effect applied so far.

      recover is all-or-nothing. The paper names this as one of the two limits of the bare track/recover model. That is why the calculus moves on to effect functions and iterators. Per-component teardown comes from nesting instead: each fiber runs in its own context with its own φ.

      The paper models activation as an effect iterator: each step yields a state change, its inverse and a continuation. That is what makes a half-finished activation revertible, not just a completed one.

          What happened, in order

            Two things to notice:

            • The teardown order is automatic. Removing database stops commands first, then auth, then database. Nobody wrote that order. It comes from the declared needs.
            • The undo stack empties exactly as far as it filled. No entry outlives the component that made it.
            export const name = 'auth'
export const inject = ['db'] as const

export function apply(ctx: Context<{ db: Database }>) {
  // ctx.db is never undefined while this component runs:
  // if db goes away, the runtime stops auth first
  ctx.set('auth', new Auth(ctx.db))
}

            Classical dependency injection does not do this. A container injects once, at construction. Here the binding is live. A provider can go away, and the runtime handles that as carefully as it handles a new one.

            04

            The lifecycle of one component

            Four states, nine rules, and one rule that keeps activation safe.

            The runtime instance of a component is a fiber. A fiber moves between four states: Inactive, Reloading (starting up), Active and Unloading. The paper says Reloading because a fiber enters it on every restart, not only the first.

            The rules come in two kinds. O- rules are what the orchestrator may do: insert or retire a fiber. L- rules are steps the runtime takes by itself, whenever their conditions hold. Press the buttons and follow the highlighted edge.

            The ninth rule, O-Retire, only raises a retirement flag. It applies in every state, so it would be a loop on all four boxes. The paper's figure leaves it out, and so does this one.

            What happened, in order

              L-Divert is the safety rule. Suppose a dependency changes while a fiber is still starting. The fiber does not finish against a stale environment. It goes straight to Unloading. The changes it already made are on its undo stack, so the rollback is complete although the activation was not.

              Removal takes several steps. O-Retire raises a flag. L-Leave and L-Unload take the fiber down to Inactive. Only then may O-Remove drop it. Dropping an Active fiber outright would throw away its undo stack and leak everything on it.

              Going deeper: the exact conditions

              L-Divert has two forms. One lands the iteration in flight and keeps its inverse, the other aborts it. Routing through Unloading rather than Active is what stops a fiber from provisioning its coeffects for the length of one more step.

              O- rules are actions the orchestrator may take: their premises say when the action is legal, not when it happens.

              Insertion and retirement are the orchestrator's only inputs; it never sets a lifecycle state directly. O-Remove is guarded by premises that the fiber is retired, Inactive, provisioning nothing, and parent to no one.

              L-Unload carries a premise of its own — ¬relied: no other installed fiber may currently resolve one of its declared keys to this one. A provider that has decided to leave therefore sits in Unloading, already out of service and provisioning nothing, until every consumer has gone. That single premise produces the teardown order in section 03. The test is against committed views rather than declarations, so a consumer that has already unloaded stops counting — the guard releases itself, with no reference count kept anywhere.

              Reconfiguration is not a method on the fiber. The declarative loader owns it: the orchestrator edits a configuration record, and the loader reconciles the difference into fiber operations — for a changed config, a dispose and a fresh ctx.use, leaving every untouched entry running.

              05

              What the runtime guarantees

              Two properties. The machinery exists to prove them.

              1. Removal undoes the component exactly

              Remove a component, and the context returns to where it would be had the component never been added. This holds even when other components changed the context in the meantime.

              "Returns" means observationally equivalent, not bit-identical: no available operation can tell the two states apart. Without that weakening, the theorem would be false for any real system with caches and counters.

              2. The history leaves no trace

              Install and remove components in any order. When everything settles, the system is the same as if each surviving component had been loaded once, in dependency order. A dynamic system becomes as predictable as a static one. The paper calls this confluence.

                  Going deeper: the exact statements and their hypotheses

                  Once the system is quiescent — every fiber settled at its target view, no transition in flight — the state it comes to rest at is the state the same insertions and retirements would have produced had each surviving component been loaded once, in dependency order, and none ever unloaded.

                  The theorem is about the lifecycle rules alone, holding the orchestration steps fixed — different inputs land in different places for no interesting reason — and it carries a second hypothesis, that every component is total on its provision. What makes the two runs above agree despite different insertion orders is a separate and simpler fact: the set of fibers that ends up Active is determined by which components are present and unretired and by the dependency graph, not by the schedule.

                  Recovery exactness compares against the other fibers' effects replayed rather than against a frozen snapshot. Each binding is restored only up to what its own key's operations can observe, so — in the paper's examples — a monotone allocator is not rewound, a heap's layout does not come back from a free, and a message already sent stays sent. A location the system reifies at no key is outside the calculus altogether.

                  06

                  Why it matters: a harness that rewrites itself

                  The case the paper looks ahead to, and where the usual workaround fails.

                  A harness is the runtime around a model. It composes tools, manages permissions, session state and memory, and runs subagents. The paper's forward-looking case is a harness that changes its own components while it serves requests. Tools that a model writes for itself are an early form of this.

                  Such changes arrive often and with little human oversight. Without this discipline, each one costs a full process restart:

                  • The restart throws away process state: caches, open connections, work in progress. Rebuilding it takes seconds to minutes.
                  • In-flight tasks break over and over. To stay available, you pay for redundant replicas.
                  • A faulty change can disable the very process you need to recover from it.

                  Without the dependency half, the failure is quieter. Each module must notice by itself when a dependency appears, disappears or changes. Naive code replacement breaks dependents silently, or adds a circular dependency that shows up only at reload time.

                  All of it, on one bench

                  This harness holds a session cache and serves requests. It can redeploy its tool suite underneath itself. Try the buttons in order:

                  2. Deploy one that throws. Its second change raises an error. The runtime undoes the first change, keeps the error on the fiber and does not retry. The old build comes back.

                    What happened, in order

                      Why not just restart?

                      Operating systems already give you clean removal, but per process. Container orchestrators already handle dependencies, but per service. Both work at a coarse grain, while the code inside composes at a fine grain. A container cannot express a dependency between two parts of one process. It pushes onto the network what could be a local function call. That gap is what this paradigm aims at.

                      The everyday cases

                      • Plugin systems. Cordis runs Koishi and its 4000-plus community plugins. You install, remove and reconfigure them live, without a restart.
                      • Hot reload that cleans up. Ordinary HMR swaps the module and leaves the old listeners and registry entries behind. Effect tracking does that bookkeeping for you.
                      • A pattern you can use without the framework. Make every effect return its inverse. Keep the inverses on a stack. Unwind in reverse.
                      07

                      Where it stops

                      Not every change can be undone.

                      The runtime can undo only what it owns. An effect is revertible only where the system can change a location exclusively and restore what was there before. A direct process.on or a change to somebody else's object is outside that line. The runtime does not track it.

                      The line is per location, not per medium. A scratch file under a private path is inside. The same path shared with another program is outside. A coeffect can move the line: if every access goes through operations that supply an inverse, the location becomes tracked.

                      What leaves the system stays gone. open and close, malloc and free are ordinary revertible effects. The bytes a write sends are not. For those, you hold the output back until the state is certain, or you compensate: delete the file, refund the charge. Compensations unwind in the same reverse order as inverses. The paper notes that the proofs must then be redone against a coarser equivalence.

                      Hostile code needs a real boundary. Declared inject plus context interception already give capability-style access control: an undeclared access throws, and the full set of requests is known before the component runs. An orchestrator can narrow any component's access without touching the provider. But code that reaches the host runtime directly ignores language-level checks. Untrusted components need a sandboxed process, a separate runtime or a container. The bridge to it appears on the host side as an ordinary fiber with the same narrowed capabilities.

                        

                      Glossary

                      component
                      A plugin: code with an apply(ctx) function, plus what it needs (inject) and what it provides.
                      fiber
                      The running instance of a component: its dependencies, its provisions, its own context and undo stack.
                      context (ctx)
                      The one object through which a component changes anything and gets anything. The runtime sees every change because of it.
                      effect, inverse
                      A change a component makes, and the function that undoes it. Revertible effects always come in pairs.
                      coeffect
                      What a component needs from its environment, such as a db service. The dual of an effect.
                      Σ (sigma)
                      The service table: which services are provided now, and by whom.
                      φ (phi)
                      The undo stack: the inverses of every effect applied so far, newest on top.
                      γ (gamma)
                      The current state of the context.
                      orchestrator
                      Whoever decides which components exist: a person, a config loader, or the harness itself. It can only insert and retire.
                      O- / L- rules
                      Steps of the calculus. O- rules are what the orchestrator may do. L- rules are what the runtime does by itself.
                      quiescent
                      Settled: every fiber is in its target state and no transition is in flight.
                      observationally equivalent
                      Two states that no available operation can tell apart, even if their bytes differ.
