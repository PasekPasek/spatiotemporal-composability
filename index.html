A walkthrough of arXiv:2608.25512 (Shi, Zhang and Cui, 2026)

Spatiotemporal composability

You disable a plugin in your editor and it asks you to restart. Not because the code is still loaded, but because nobody knows what that plugin changed. This is a runtime that knows — and this page lets you operate it.

Four sandboxes, each isolating one mechanism. Everything is live: install components, watch the inverse stack unwind, break a dependency mid-activation and see what the runtime does about it.

01

Two orthogonal axes

Time and space, each with its own mechanism.

Time. Removing a component has to undo everything it did. The mechanism is revertible effects: every transformation of the context carries its own inverse, and the runtime holds onto it.

Space. A component declares what it needs from its environment, and the runtime manages that reactively. The mechanism is reactive coeffects: every change to the context is classified against a component's declaration and drives its activation or deactivation.

An effect is what a component does to its environment. A coeffect is what it requires from it — the dual notion, familiar from static analysis, lifted here into a runtime mechanism. Ordinary plugin code has neither property:

// the author has to remember the inverse of every line — and never does
export function apply(bus: Bus, services: Registry) {
  bus.on('message', onMessage)
  const timer = setInterval(poll, 1000)
  services.db = new Database()
  // dispose()? in practice: a leaked listener, a zombie timer, a dead registry entry
}

The paper's own move is to unify the two axes rather than bolt them together: the effect context and the coeffect context collapse into a single context type, and every effect and every coeffect is mediated through it. That discipline is what it calls the context paradigm, and the mediation is what induces the observational equivalence up to which two components' effects interleave without disturbing one another.

02

The runtime, hands on

Four components, one context. Install and remove them in any order.

Each component declares what it injects and what it provides. The left column is the system; the right is the context it shares — the service table Σ and the accumulated inverse stack φ. Try removing database while everything is running.

        Two things are worth noticing. Removing database takes auth and commands down with it, deepest dependent first — nobody wrote that teardown order, it falls out of the resolution. And the inverse stack empties exactly as far as it filled: no entry survives its owner.

export const inject = ['db'] as const

export function apply(ctx: Context<{ db: Database }>) {
  // ctx.db is non-null for the entire lifetime of this fiber:
  // if db goes away, the fiber is torn down before it can observe undefined
  ctx.set('auth', new Auth(ctx.db))

        This is the part classical dependency injection does not do. A container injects once, at construction. Here the binding is live, it can be withdrawn, and withdrawal is handled as carefully as provision.

        03

        Revertible effects: track and recover

        The context stops being a state and becomes a state plus an accumulator.

        An ordinary context Γ is lifted to a revertible one, ∂Γ = Γ × (Γ → Γ): the current state γ together with φ, the composition of the inverses of every effect applied so far.

        track(f, g) applies f to the state and appends g to the accumulator. recover applies the accumulator. Order is the whole game — inverses come off in reverse, like a stack.

        γ — context state

          φ — accumulated inverses

            Apply a few effects, then step back through them one at a time.

            In Cordis, the TypeScript reference implementation, this collapses into a single call. The effect returns its own inverse and the runtime keeps it:

            export function apply(ctx: Context) {
  // explicit effect: forward and inverse in one place
  ctx.effect(() => {
    const timer = setInterval(poll, 1000)
    return () => clearInterval(timer)
  })

  // context APIs are tracked already — the inverse is derived for you
  ctx.on('message', onMessage)
  ctx.set('db', new Database())
}

            The whole temporal idea, in one class

            Strip away the ergonomics and the mechanism is a stack of functions. Note that set and on never touch that stack themselves — both are built on effect, because every context-mutating operation reduces to a ctx.effect call:

            type Dispose = () => void

class Ctx {
  private phi: Dispose[] = []                      // φ — accumulated inverses
  private sigma = new Map<string, unknown>()        // Σ — coeffect context
  private watchers = new Map<string, Set<Dispose>>()
  constructor(private bus: EventTarget) {}

  /** track(f, g): run the effect, keep the inverse it hands back */
  effect(f: () => Dispose): Dispose {
    const g = f()
    this.phi.push(g)
    return g
  }

  /** providing a service is itself a revertible effect */
  set(key: string, value: unknown): Dispose {
    return this.effect(() => {
      const had = this.sigma.has(key), prev = this.sigma.get(key)
      this.sigma.set(key, value)
      this.notify(key)
      return () => {
        had ? this.sigma.set(key, prev) : this.sigma.delete(key)
        this.notify(key)
      }
    })
  }

  /** a tracked context API: the caller never writes this inverse */
  on(event: string, fn: () => void): Dispose {
    return this.effect(() => {
      this.bus.addEventListener(event, fn)
      return () => this.bus.removeEventListener(event, fn)
    })
  }

  /** recover: φ(γ) — inverses in reverse order */
  recover(): void { while (this.phi.length) this.phi.pop()!() }

  private notify(key: string): void {
    this.watchers.get(key)?.forEach(fn => fn())
  }
}
            The paper goes further and models activation as an effect iterator: each step yields a state change, its inverse and a continuation. That is what makes a half-finished activation revertible, not just a completed one.
            04

            Fiber lifecycle

            A fiber is the runtime instance of a component: dependencies, provisions, effect iterator.

            The calculus is nine rules over four lifecycle states, plus an empty node for a fiber absent from the registry. O- rules are actions the orchestrator may take: their premises say when the action is legal, not when it happens. L- rules are steps the system takes unprompted, whenever their premises hold. The paper's name for the loading state is Reloading — a fiber re-enters it on every reactivation, not only the first.

            The ninth rule, O-Retire, only raises the retirement flag and applies at every state, so it would be a self-loop at all four nodes; the paper's figure omits it and so does this one.

              L-Divert is the safety rule. If a dependency changes while a component is still activating, the fiber is diverted straight to unloading rather than finishing against a stale environment. The effects it already applied are in the accumulator, so the rollback is complete even though the activation was not. It has two forms: one lands the iteration in flight and keeps its inverse, the other aborts it — routing through Unloading rather than Active is what stops a fiber from provisioning its coeffects for the length of one more step.

              Why removal is two rules, not one

              Insertion and retirement are the orchestrator's only inputs; it never sets a lifecycle state directly. So O-Retire raises a flag and nothing more, and the lifecycle rules carry the request out — L-Leave down to Unloading, L-Unload back to Inactive, and only then may O-Remove drop the entry, guarded by premises that the fiber is retired, Inactive, provisioning nothing, and parent to no one. Dropping an Active fiber outright would discard its accumulator and leak exactly what the accumulator exists to reclaim.

              const fiber = ctx.use(auth, { secret })

// fiber.dispose *is* the accumulator; awaiting it recovers the context
await fiber.dispose()

              Reconfiguration is not a method on the fiber. The declarative loader owns it: the orchestrator edits a configuration record, and the loader reconciles the difference into fiber operations — for a changed config, a dispose and a fresh ctx.use, leaving every untouched entry running. That is the sense in which a config change is reconciliation rather than a process restart.

              05

              What you get in return

              The two properties the machinery exists to prove.

              Recovery exactness

              Removing a component restores the context to a state observationally equivalent to the one before it was added — even if other, independent fibers applied their own effects in the meantime, which is why the statement compares against those effects replayed rather than against a frozen snapshot. Observational, not bit-identical: what matters is that no available operation can tell the two apart. Without that weakening the theorem would be false for any real system with caches and counters.

              The weakening is also the limit. Each binding is restored only up to what its own key's operations can observe, so — in the paper's examples — a monotone allocator is not rewound, a heap's layout does not come back from a free, and a message already sent stays sent. A location the system reifies at no key is outside the calculus altogether.

              Confluence

              Once the system is quiescent — every fiber settled at its target view, no transition in flight — the state it comes to rest at is the state the same insertions and retirements would have produced had each surviving component been loaded once, in dependency order, and none ever unloaded. The dynamic history leaves no trace, and the normal form it converges on is the statically assembled system. That is what makes a dynamic system as predictable as a static one.

              Two caveats the demo below cannot show. The theorem is about the lifecycle rules alone, holding the orchestration steps fixed — different inputs land in different places for no interesting reason — and it carries a second hypothesis, that every component is total on its provision. What makes the two runs below agree despite different insertion orders is a separate and simpler fact: the set of fibers that ends up Active is determined by which components are present and unretired and by the dependency graph, not by the schedule.

                  06

                  Why a TypeScript developer should care

                  Where the absence of this discipline actually costs you.

                  Self-modifying agent harnesses

                  A harness is the runtime around a model: it composes tool suites and execution environments, governs permissions and sandboxing, keeps session state, manages context and memory, and orchestrates subagents. The paper's forward-looking case is a harness that generates and deploys modifications to its own components while it is still serving requests — model-synthesised reusable tools being the narrow precursor already in use. Every one of those modifications is an instance of dynamic composition.

                  Because they land continuously and with little or no human oversight, the usual fallback stops being viable. Without temporal composability each self-modification is a full process restart that discards everything process-local: caches, open connections, partial computations. Rebuilding that takes seconds to minutes. At self-modification frequency the unavailability accumulates, in-flight tasks are disrupted over and over, and — the failure mode worth sitting with — a faulty self-modification can disable the very process you would need in order to recover from it.

                  Without spatial composability the failure is quieter and arrives later. Every module has to notice for itself when a dependency appears, disappears or changes identity, and can only do so by ad hoc means. A naive code-replacement strategy breaks dependents silently, or introduces a circular dependency that surfaces at reload time rather than at the moment the change was made.

                  Why restarting the process is not the answer

                  Operating systems already provide temporal composability — at the granularity of a process. Container orchestrators already provide spatial composability — at the granularity of a service. That substitute is a large part of why the problem has attracted so little formal attention: most software simply tolerates the gap.

                  It is not free. A restart discards accumulated state and takes seconds to minutes to rebuild, so staying available across one means running redundant replicas — paying in hardware for the inability to recover a single component. Container-level orchestration cannot express a dependency between two components sharing an address space, and pushes onto the network what could have been a local function call. Both mechanisms sit at the process and container boundary, while the systems built on them compose at a far finer grain. That mismatch is the gap this paradigm aims at.

                  The everyday cases

                  • Plugin systems. Cordis is the meta-framework behind Koishi and its 4000-plus community plugins: install, uninstall and reconfigure live, without restarting the process.
                  • Hot reload that actually cleans up. Ordinary HMR swaps the module and leaves the old listeners and registry entries behind. Effect tracking does that bookkeeping for the plugin author.
                  • A pattern you can steal without the framework. Make every effect return its inverse, keep them on a stack, unwind in reverse. That is the entire temporal mechanism.

                  Where the discipline stops

                  An effect is revertible only where the system can modify a location exclusively and restore what was there before. Outside that line an operation is untracked and acts as the identity — a direct process.on, a mutation of somebody else's object. The paper's point is that the line is drawn per location rather than per medium, and that a coeffect can move it: reifying an external location confines access to a set of operations that can each supply an inverse, and what acted as the identity becomes tracked. A scratch file under a private path is inside; the same path shared with another program is outside.

                  What crosses irreversibly is emission, not acquisition. open installs a descriptor that close removes and malloc reserves a block that free releases — those records live inside the boundary and are ordinary revertible effects. The bytes a write pushes through the descriptor are gone. Recovering from those means withholding the emission until the state is certain, or compensating for it — deleting the file, refunding the charge — and compensations compose in the same LIFO order as inverses, though the metatheory has to be re-proved against the coarser equivalence they satisfy.

                  On hostile code the paper is more specific than "no defence". Declared inject plus context interception already amount to capability-style access control over proxy-mediated dependencies: an undeclared access throws, the full set of requests is known before the component runs, and an orchestrator can attenuate any component's access without touching the provider. But language-level checks are moot against code that can reach the host runtime directly, so genuinely untrusted components need an execution boundary beyond the language — a sandboxed process, a separate runtime, a container — with the bridge showing up on the host side as an ordinary fiber whose capabilities can be attenuated the same way.
